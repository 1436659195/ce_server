## 4. 与文档假设的偏差

1. **“jupyterlab 4.x 的 `pip install jupyterlab` 不自带 terminado”** —— 本机 jupyterlab 4.6.3，但 terminado 0.18.1 已随依赖安装并正常工作。该前提在本环境不成立（可能为某次安装/缓存差异；但不影响结论：terminado 是好的）。
2. **“`GET /api/terminals` 可能仍 200（核心活着）不代表终端可用，勿用 200 排除”** —— 这条提醒本身有道理，但它指向“terminado 缺失”场景；本机 `POST` 建终端与 `WS 101` 都成功，**确实可用**，故“可用 / 不可用”的二分在本机落在“可用”一侧。
3. **“`Unable to connect` 多半是旧 Jupyter 死/换口”** —— 本机 jupyter pid 44165 全程稳定、端口未变，`Unable to connect` 出现在**中继断开**那一段（见下方第 5 节），更像是中继 WS 抖动，而非本机 Jupyter 地址失效。

## 5. 真实根因（被控机侧能确认的部分）

### 5.1 终端路由的“冷启动 / 配对竞态”404
- 日志里所有 `404 GET/POST /api/terminals` 都**精确对齐手机（重）配对 / 离开事件**（19:03:17、19:21:28 等），且请求确实打到了本机 jupyter（ServerApp 记录了 404）。
- 但同一进程、同一 token，在**静止状态**下（无手机活动）我做了 2 分钟 ×8 次轮询，`/api/terminals` **连续 8 次 200 `[]`**，零 404。
- 当前（19:28）实测 `POST 200` + `WS 101` 全绿，而日志里 19:21 还是 404 → 证明这是**单进程内 terminals 路由在“刚被 ce 拉起 / 重新（重）配对触发校验”那一下还没就绪，随后即恢复**的瞬时窗口，不是永久性缺失。
- jupyter 进程**未重启**（pid 44165 从 18:50 起稳定），ce 也**没有**在 404 后重启 jupyter；属于 ce 内部时序/生命周期问题，而非“进程死了 / 地址错”。

### 5.2 中继连接抖动（近期新增，可能是“还是不行”的更直接成因）
- 最新 `ce.log` 末尾出现一段中继 `WebSocket connection to 'wss://ce.coding-everywhere.xyz/?cid=...' failed: Failed to connect`，并多次退避重连（2s→4s→8s→16s→30s），随后 `已连中继`。
- 这段与 Jupyter 无关，是**被控机 → 中继**这条链路本身的瞬时失败。若用户此刻“还是不行”，更可能是中继没连上 / 手机端连的是断开态，而不是本机终端插件问题。
- 建议中继侧核对：是被控机网络瞬时抖动，还是 `ce.coding-everywhere.xyz` 服务端在该时段有抖动。

## 6. 给开发者的建议

1. **修正诊断文档（第 2 步）**：
   - WS 判据必须用**真实终端名**：先 `POST /api/terminals` 建一个，再对该名做 `WS /terminals/websocket/<name>`，**101 = terminado 正常**；只有“真实名也 404”才指向路由缺失。
   - 删除/标注 `/websocket/probe` 假名测试：假名 404 是预期行为，会误导为 terminado 缺失。
   - 明确：`GET /api/terminals 200` 与 `POST 建终端 200` 都可单独作为 terminado 已加载的证据，不要仅凭其一就排除。
2. **ce 侧修复竞态**：手机（重）配对 / 列终端时，对 `/api/terminals` 做**有限重试 + 退避**，不要首错即降级为空列表；列终端前应轮询确认 terminals 扩展已加载（200 而非首错即弃）。
3. **中继侧排查抖动**：关注被控机→中继 WS 的 `Failed to connect` 与 30s 退避，确认是服务端瞬时故障还是被控机网络。
4. **复现协作**：若需抓“ce 来源的真实失败请求”，可在手机（重）配对的同时由被控机实时对拍 `GET/POST /api/terminals`（我可配合实时抓取并对比直接 curl 的差异）。
