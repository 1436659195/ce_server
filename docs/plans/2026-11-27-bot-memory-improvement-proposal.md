# 数字人记忆改进方案（讨论稿）

目标：让数字人记住主人长期希望怎么做，避免把某次任务的要求带进以后的所有聊天；主人明确要求记住时，能够确认到底保存了什么。

实现方向：沿用现有 SQLite、Router 和后台记忆整理员，统一写入和校验。第一版以 CE 后端为主，保持手机现有字段和管理操作兼容。

## 1. 目前的问题已经发生在哪里

本机只读核查结果：共 13 条记忆，10 条生效且均为长期，另有 2 条过期、1 条被替代。13 条都能找到对应原话。问题集中在适用范围和自动升级。

| Bot | 实际记忆 | 问题 |
| --- | --- | --- |
| A-net研发 | 本次设计文档用 HTML 交付 | 是某份文档的交付要求，被升成长期 |
| A-net研发 | 在原 HTML 上修改，不重新制作 | 是同一次任务的修改边界，被升成长期 |
| A-net研发 | 本次说明包含五个改造点 | 五个点来自当时的具体方案，被升成长期 |
| walle | 此次排查思路精简，按顺序和条件分支说明 | 原话是在要求重写一份 TXT，被升成长期 |
| ce服务维护 | 完成后只回“已解决”，不要解释验证依据和方法局限 | 从版本对比场景扩大成一般任务汇报规则 |

前四条关联的任务已经完成。它们最初都是中期，后来由宿主自动升长期。普通字词命中也会增加计数，创建时计数已经是 1，因此聊到类似内容两次就可能达到升级门槛。

## 2. 先决定这句话应该存在哪里

| 用户表达 | 放在哪里 | 生命周期 |
| --- | --- | --- |
| “以后给方案，至少给 MD 文档，讲清问题和改法” | 长期记忆 | 持续有效，用户可以修改或取消 |
| “最近这几天回答简短一点” | 中期记忆 | 按用户明确期限；未说明期限时采用默认期限 |
| “这份文档改成 HTML，沿用原来的文件” | 当前工单的输入、交付要求和执行指导 | 对这个任务生效，任务历史保留 |

后台整理员要区分“持续偏好”“阶段偏好”“具体任务要求”。依据整句话和任务上下文判断，不能只靠有没有“以后”“记住”两个词。

例如“排查步骤写得太啰嗦，重写这份 TXT”，先落实到这份任务。不能自行改写成“主人以后所有排查材料都必须如此”。将来主人明确说“以后排查步骤都这样写”，再保存为长期偏好。

现有任务账本已经保存原话和执行指导，优先使用它承载具体任务要求。

## 3. 取消按次数自动升长期

删除“触发计数达到 3 就升长期”的规则。命中次数只说明这条记忆与多少轮文字发生了关联。

长期记忆通过语义和来源确定：

- 新要求本来就在表达持续偏好，可以直接保存为长期。
- 原来是中期，主人后来明确要求持续执行，可以更新为长期，追加这次原话来源。
- 仅仅多次命中、同一任务聊得久，都不升级。
- 不能确认长期性时，不自动扩大范围；具体任务要求留在工单中。

不另加一轮“升级判断模型”。现有 Router 或后台整理员已经需要理解本轮意图，由它们提出带依据的变更，宿主检查真实来源和写入条件。

中期记忆优先服从明确期限；无明确期限时，第一版保留现有 10 轮或 7 天的默认值，先到为准。这个默认值不再决定具体任务要求是否还有效，因为任务要求由工单承载。

## 4. 自动整理和明确要求共用一个保存入口

保留两条入口：

1. 后台整理员自动识别值得记住的偏好。
2. Router 遇到主人明确要求记住、修改或取消规矩时，可以直接调用记忆工具。

两者共用同一套宿主写入逻辑，避免后台和 Router 分别写出两份。

保存时记录：规则正文、长期或中期、适用范围、期限、来源消息和原话、版本、修改说明。范围和主体不能只存在一段自然语言里：至少区分当前 Bot 的通用偏好、指定卷宗、指定任务；仍有其他适用条件时保留简短说明供 Router 理解。

Router 收到实际保存回执后，才能说“已记住”。回执包含编号、版本和保存后的正文，让它有能力准确复述。保存失败时如实说明。

写入还要满足这些条件：

- 主体和 Bot 身份由宿主绑定，来源必须是实际用户消息。
- 修改现有规则需要编号和预期版本；并发冲突不能静默覆盖。
- 重试请求有幂等回执；同一原话中的同一主题不因两条入口重复新增。
- 内容去重先查当前相关记忆；含义相同由模型提出更新目标，宿主不做模糊自动合并。
- 一条记录表达一个独立主题。一次提出多条规矩时允许逐条保存，每条都有回执。
- 后台只有提交了有效的“无需记忆”判断，或取得真实写入结果，才能把整理任务标为完成；缺少提交或校验失败要留失败原因。

完整旧版本和变更流水保留。用户消息撤回、主人暂停或作废记忆，继续走现有管理逻辑。

## 5. 使用时先检查范围，再交给 Router 理解

先由宿主筛选同一 Bot、渠道、发言者，并校验结构化任务或卷宗范围和有效期。属于旧任务的要求不会因为出现“文档”“问题”等词，就进入新任务的通用记忆。

当前每个 Bot 最多只有 5 条有效长期记忆，没有必要引入向量数据库。第一版沿用字词召回和 Router 语义判断：

- 数量在现有预算内时，带入全部适用的长期规则和相关中期偏好。
- 字词重合用于找候选，不作为“已遵守”的证明，也不决定升长期。
- 超出注入上限时提供总量、遗漏提示和分页查询入口，不能只按最近更新时间截断，让旧规矩无声消失。
- 查询和修改都限定当前 Bot 的授权范围。

Router 把执行相关的约束写进派工指导；Worker 不需要复制整份偏好库。回复口吻之类的规则主要由 Router 遵守。

定时任务的运行时间和执行状态以调度器为准。记忆可以表达“主人希望每天核对版本”这一约定，实际建立或修改计划必须取得事件工具回执。

执行后预计保留 6 条有效长期记忆。退出常驻的 4 条保留记录、原话和调整原因；已有的 3 条历史记录也保留。

这是针对已核对的具体记录的清理，不按“本次”等字眼批量删除其他记忆。每项都先检查当前版本、来源和关联任务，发现期间有新修改则停止该项，重新核对。

## 7. 开发顺序和验收

### 第一步：修正归类和升级

修改 `src/cli/bot-runtime/memory.ts` 中的整理提示、提案校验和选择逻辑，以及 `service.ts` 中的 `sweepMemories`。

先在 `test/bot-memory.test.ts` 补失败测试，再实现：

- “这份文件用 HTML”归入任务要求。
- 同一任务反复聊十次，不会升长期。
- “以后所有方案都给 MD”可以直接保存长期。
- 中期偏好后来被明确要求长期执行，可以更新档位并追加来源。

### 第二步：统一写入和回执

在 `types.ts`、`store.ts` 增加兼容的范围、版本和回执信息；将后台写入和 Router 工具接入同一服务。补充 `router.ts` 的工具定义和少量使用说明。

验收：重复请求不重复新增；旧版本更新冲突会被拒绝；跨 Bot 来源被拒绝；没有合法提交的后台任务不能显示成功；Router 保存后返回的正文、编号和版本可从数据库读回。

### 第三步：范围筛选和派工

调整 `service.ts` 的记忆上下文组装、后台整理上下文和派工指导。后台至少看到消息实际关联的任务、卷宗及简短目标，避免仅靠“这个”“刚才”猜对象。

验收：旧文档的要求不进入新任务；同一条规矩换一种说法，Router 仍可理解并查找；字词命中计数不影响档位；注入超量时可以查询遗漏内容；执行相关约束能传给 Worker。

### 第四步：迁移已核对的记录

先在数据库副本生成逐条变更预览，检查 5 条保留、4 条退出常驻、1 条收窄的结果，再执行有来源、有版本保护、可重复运行的迁移。运行时不重放真实聊天，也不调用真实模型完成测试。

相关测试命令：

```bash
bun test test/bot-memory.test.ts
bun run typecheck
bun test
git diff --check
```

独立审查通过后再合入。原工作区未提交的会话恢复修改继续单独保留。
