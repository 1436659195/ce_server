## 一、历史多了，每次还把整箱资料搬出来

### 现在的问题

有些地方只需要展示最近几个任务，却先把这个Bot的全部任务、卷宗、成果读出来，逐条解析，再留下少量结果。

选卷宗时，还会对每一份卷宗重新翻一遍全部任务和成果。搜索结果出来后，整理结果摘要又会重复读取这些资料。APP约每2秒刷新状态，这些读取可能被反复触发。

可以理解成：只想拿最近五份文件，却先把整个档案室搬出来，再逐柜寻找。

### 会有什么影响，为什么要改

历史较少时可能感觉不到；数量变大后，查资料和刷新状态会多占时间、内存和CPU。最后只发给模型五条，不代表前面只读了五条。

当前已有ID和Bot索引，但它们主要帮助找到记录或某个Bot的数据，不能消除“找到后全读出来再筛”的开销。指纹比较只是在选定卷宗后比较一个配置值，优先优化它帮助不大。

### 具体怎么改

1. **先把一轮内的重复读取去掉。** 同一次处理只读取一次需要的任务和成果，后面的步骤共用，不为每个搜索结果再读一遍。
2. **把任务和成果先按卷宗分组。** 一次整理出“这份卷宗有哪些任务、哪些成果”，之后直接查对应分组，不让每份卷宗都重新遍历所有记录。这是过渡改法，仍有全量读取，但能先减少重复工作。
3. **把限制条数放到数据库查询里。** 最近任务、最近成果、某卷宗的任务、待处理任务分别按条件查询，排序后只取所需记录。需要翻历史时按页读取，不在APP每次刷新时带全历史。
4. **为实际查询补索引。** 例如按Bot、卷宗、更新时间、任务状态查找。若这些信息目前都藏在JSON正文里，可选择适合的表达式索引或专门查询列；先看查询计划，再决定，不盲目加索引。
5. **把搜索与日常刷新分开。** 搜旧卷宗时才做搜索；任务卡刷新只取当前需要的状态。不要为了刷新一个状态就重新计算所有卷宗候选。

分页只是列表展示办法，不能只查最近一页再搜索，否则会把旧卷宗重新藏起来。搜索必须仍能覆盖全部符合权限的历史，可用单独的搜索表来承接。

### 怎么判断改好了

- 用虚构数据准备三档规模，例如100、1,000、10,000份卷宗，并配套增加任务和成果；同时测“打开任务卡”“刷新状态”“搜索旧卷宗”。这些是建议测试档位，不是已证明支持的容量。
- 记录每次实际读了多少条、执行几次查询、耗时、占用内存；在同一机器、同样数据上比较前后结果。
- 任务卡只显示少量记录时，数据库返回条数应与展示需要接近，不能仍返回全部历史。
- 搜索结果数量增加时，不能出现“每多一个结果，又全读一次任务和成果”。
- 建议以目标设备上连续测试的95%请求都在约定时间内返回为通过条件，具体时间在取得基线后确定，不在未测前承诺毫秒数。
- 结果内容、权限过滤、排序和翻页不能丢失或重复；活跃任务不能被历史列表分页漏掉。

## 二、旧卷宗能搜更多了，但换个说法仍可能找不到

### 现在的问题

当前搜索已经能看旧名称、摘要、任务目标和成果文件名，并支持中文分词和更合理的排序。这比只找同名标题强很多。

剩下的问题是：主要仍看文字是否出现。用户说“上次那个断线后连不回来的问题”，记录可能写成“连接恢复异常”，用词不同就可能召回不到。类似工作太多时，正确卷宗也可能排在返回的前五条之外。

### 会有什么影响，为什么要改

前台找不到原卷宗，就可能误以为是新工作，另起一卷，后续上下文被拆散。这里是风险说明，本次没有测出实际漏找比例。

### 具体怎么改

1. **先用明确关系找。** 用户引用某条消息、某份成果或某张任务卡时，优先利用已有ID找到所属卷宗，再结合本次意图判断；不要只拿那句话重新做关键词搜索。
2. **保留现在的旧名、任务和成果搜索。** 它们已经有用，继续使用；同时把搜索数据按卷宗整理好，避免为每次搜索临时拼接全部历史。
3. **分两步找候选。** 先在数据库搜索记录中较广地找出一批，再挑最相关的少量给前台。不能把“模型最终只看五条”直接当作“搜索也只能查五条”。
4. **没找到时允许换一种查询。** 例如从成果名改查工作对象，或拆开关键词；重试次数要有上限，避免一直搜索。
5. **再决定是否加语义检索。** 如果测试证明同义表达仍大量漏找，再加入“意思相近也能找到”的检索，与文字搜索合并使用。它是可选后续增强，不是第一步就必须引入的新系统。

无论采用哪种搜索，都必须限定在当前Bot和允许访问的资料内，不能因找相似内容串到其他Bot。

### 怎么判断改好了

做一组人工知道正确答案的案例：旧名、新名、文件名、同义表达、简称、隔了很久才追问、多个相似事项，以及“根本没有对应旧卷宗”。

分别记两件事：搜索候选里有没有正确卷宗；前台最后有没有选对。这样才能区分“没找到”和“找到了但判断错了”。

先保存当前命中率作为基线，再约定改善目标；明确引用成果/任务的案例必须能定位正确归属，不能跨Bot取候选。不能用“每次都有五个结果”代替“找到了正确结果”。

## 三、归卷规则更清楚了，还要防止“找到之后选错”

### 现在的问题

现在已经要求：同一成果的追问、核对、修改尽量留在原卷宗；从只读变成修改、换文件名、任务做完了，都不自动成为拆卷理由。前台也要说明新建或续接的原因。

但“必须填理由”只能保证有解释，不能证明解释正确。两个事项标题相似，可能被错误合并；同一件事改了说法，也可能被错误拆开。

### 会有什么影响，为什么要改

误拆会让前序成果和背景不容易接上；误合会让无关历史混进新任务。两种错误都要管，不能为了追求复用，把同一项目的所有事情塞进一个大卷宗。

### 具体怎么改

1. **分清对象、任务、会话。** 卷宗代表一条持续工作链；每次新交付可以建新工单；底层session只保存执行上下文，不能用“这个session能恢复”来证明应归同一卷。
2. **给前台更可靠的关联证据。** 优先提供被引用成果、对应任务、当前工作对象和最近相关进展，减少让模型只靠标题猜。
3. **明确关联时加宿主校验。** 对明确引用旧任务/成果的请求，校验所选卷宗与引用对象归属是否相符；用户明确提出独立新事项时，仍允许有依据地新建。不能把引用旧资料一律理解为必须续接。
4. **两个对象都合理时才问一句。** 明确知道是哪份成果时直接承接；确实有两份同名文档才让用户选择，避免每次都追问。
5. **保留判定记录。** 记录选了哪卷、依据了哪个任务/成果、为什么新建，便于发现错在哪里。只保留必要依据，不记录完整思维过程。

后续若提供归错后的纠正操作，必须明确移动的是哪张工单和哪些关联资料；不能简单把两份session拼接。这个管理功能可后置，不属于本轮最小改进。

### 怎么判断改好了

- “总结文档→核对差异→修改另存”应在同一工作链中；工单可变，卷宗不应只因动作变化而变。
- 同项目的两个独立问题，应允许分卷，不因都叫“系统问题”就合并。
- 原任务只读，后续要求修改时，沿用卷宗但重新取得当前工单的相应权限，不能继承旧授权。
- 暂停、完成、隔天继续、换标题后追问，都要覆盖。
- 人工标注预期归属，统计误拆、误合、必要澄清和多余澄清，不只看总任务成功数。
- 真实模型要重复跑几轮，因为同一句话并不保证每次判断相同；一次通过不能代表准确率稳定。

## 四、APP的session标识已经接上，重点是验证真实运行

### 现在的问题

这项当前属于**验证缺口，不是已确认故障**。

源码已有完整路径：新执行先清掉旧标记；创建或恢复会话、启动轮次成功返回后，后端记录来源；任务快照返回APP；现有任务卡显示“继承 session”或“新开 session”。没有明确来源时不冒充新建，也不显示内部session ID。

但代码存在，不等于手机装的包、机器运行的后端都已经是这份代码，也不等于真实恢复过程已经测过。

### 具体怎么改进

1. **先核对运行版本。** 记录测试APK及后端构建对应的源码版本或内容指纹。这里是后续验收步骤，本方案不要求现在发布或替换服务。
2. **沿现有界面验证。** 不增加页面，只看任务卡标识是否跟随本次执行的真实来源。
3. **排队和启动中保持未知。** 不提前展示新建；新run不能遗留上一次的“继承”标记。
4. **失败如实显示。** 当前恢复失败会使工单失败，没有自动换新会话继续。因此失败不能误报“新开 session”。若未来加入恢复失败后新建的机制，再单独说明原因并验证，不能先在UI假装已有该能力。
5. **验证刷新和切换。** 切换任务、重新打开APP、网络失败后恢复，都应展示对应任务的确认结果，不把另一张工单的状态带过来。

### 怎么判断改好了

| 场景 | 预期 |
| --- | --- |
| 首次执行，没有旧会话 | 实际创建并启动成功后显示“新开 session” |
| 同卷宗、配置相同 | 实际恢复并启动成功后显示“继承 session” |
| 同卷宗、配置已变化 | 实际新建并启动成功后显示“新开 session” |
| 仍排队或来源未确认 | 不显示这两个确认标识 |
| 旧后端不返回来源字段 | 不误显示“新开 session” |
| 恢复失败 | 显示任务失败，不冒充新建成功 |
| 创建成功但启动轮次失败 | 不提前报告本次执行已确认来源 |
| 一个任务完成很快 | 完成后的任务卡仍保留本次正确来源 |
| 切换任务、重新进入或网络恢复 | 不串任务，不被旧响应覆盖新状态 |

验收时同时留后端实际创建/恢复记录、APP快照和截图，三者要对应同一工单与执行批次。仅凭截图或模型说“我继承了”都不够。

## 建议按这个顺序推进

| 顺序 | 工作 | 完成后得到什么 |
| --- | --- | --- |
| 1 | 先保存当前基线：读取条数、耗时、搜索命中、归卷案例；快速跑一遍session标识真实联调 | 知道哪些是实际问题，哪些只是待测风险 |
| 2 | 去掉同一轮重复读取，任务/成果先分组；再做数据库按需查询和分页 | 历史增加时不必每次搬出整箱资料 |
| 3 | 建立覆盖旧名、任务、成果的搜索记录和明确引用定位；按需再加语义召回 | 先把正确旧卷宗找出来 |
| 4 | 用误拆/误合案例检查前台决策，补归属校验和必要澄清 | 找到后也能选对 |
| 5 | 在目标设备和目标历史规模下回归全部流程 | 确认优化没破坏权限、交付和已有session行为 |

每一步都先保存改前结果，再与改后对照。不要为了证明“已经优化”而只测十条历史，也不要只看平均耗时而忽略特别慢的请求。
