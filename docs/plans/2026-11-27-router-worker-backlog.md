# Router 与 Worker 协作五项改进

记录日期：2026-11-27。五项确认需求已在源码实现，自动化验收与实际运行边界见 [验收记录](2026-11-27-router-worker-verification.md)。日历与事件唤醒仍暂缓。

## 1. Router 校验交付并驱动 Worker 修正

状态：已实现，未部署。

- Router 作为主 Agent，负责目标理解、派工、结果校验、纠偏及最终交付；Worker 保持持续会话和复杂任务执行能力。
- Worker 交付文件时，为每个文件附带结构化摘要，对照用户要求说明完成情况、验证结果及遗留问题，并关联对应文件与版本。
- Router 默认审查摘要；发现矛盾、缺项，或用户明确要求核对原文时，再按需查看文件。
- Router 发现结果偏离原需求时，可在原目标及授权范围内，把具体问题和修正要求退回 Worker；Worker 修正后重新提交，Router 再次检查。
- 对外回复的字数与格式限制见第 2 项；内部交付摘要须保留核验所需信息，不套用对外气泡的限制。

实现：Worker 通过 `work_finish.artifactSummaries` 提交逐文件摘要，宿主绑定实际附件 hash/revision；Router 默认审摘要，必要时 `artifact_read` 抽查文本片段。`revise` 绑定本轮结果、工单与版本，原工单增加 correction 输入并续接同卷宗会话；旧结果取消，验收通过后才交付与记录经验。

实施边界：最多自动返工三轮；保留原授权、目标和验收要求。Worker 完成后显示“核对中”，Router 接受后标记 approved；停止、权限切换会取消待验收交付。摘要合计最多 8000 字符，文件交付最多 4 个附件；二进制附件需要 Worker 提供检查，Router 不直接解析。

## 2. 按回复类型设置字数、格式与附件交付规则

状态：已实现，未部署。

| 本次回复类型 | 气泡正文合计上限 | 格式 |
| --- | --- | --- |
| 纯聊天、未包含 Worker 结果的回复 | 100 个可见字符 | 纯文本，不使用 Markdown |
| 包含 Worker 文字结果的回复 | 500 个可见字符 | 允许 Markdown |
| 附件交付 | 100 个可见字符 | 纯文本气泡加实际附件，不使用 Markdown 气泡 |

- 以本次回复是否表达 Worker 结果为依据；历史上调用过 Worker，不改变当前普通聊天的限制。刚派工、结果尚未返回的受理话仍按 100 字纯文本处理。
- 上限按一次完整回复的全部气泡合计计算，不通过拆分气泡规避；上限不是每次必须写满的目标。
- Router 判断结果结构复杂、适合单独阅读时，要求 Worker 整理成附件，再以一句简短纯文本说明交付，例如“详细对比整理好了，请看附件”。
- 附件须实际生成并关联成功后才可交付；正文路径或口头承诺不能代替附件。
- 此流程依赖第 1 项的 Router 向 Worker 追加要求并接收修正或新结果的能力，在原目标及授权范围内完成。

实现：宿主按本轮实际 Worker 来源和附件绑定策略；混合回复整组计数，单独的普通聊天仍遵守 100 字纯文本。Markdown 字数按可见文字保守计数，原文另设 8000 字符上限；显式 format 经加密消息传到前端，客户端仅为 Bot 的 Markdown 文字结果渲染，禁用原始 HTML。

## 3. Router 按需将执行要求和经验写入工单

状态：已实现，未部署。

- Router 在每次派工或补充任务时，结合当前需求，从身份设定、用户记忆和经验中判断哪些内容与本次执行有关，将必要的约束、经验及验收要求明确写入工单或补充指令。
- 不向 Worker 全量复制 Router 的记忆或提示词；仅面向前台交流的要求不自动成为 Worker 的执行约束。例如“报告保留原文引用”应传递，“聊天不超过 100 字”不应限制 Worker 的文件内容或内部汇报。
- Worker 保留宿主提供的固定系统提示词，Router 提供本次任务指令；任务及经验文字不能覆盖宿主的真实能力、权限和目录边界。
- 本项解决派工时相关要求可能漏传的问题，采用 Router 按需筛选与转译的方式，不引入全量记忆同步机制。

## 4. 细化历史对话查询工具

状态：已实现，未部署。

- 支持开始时间、结束时间和自定义返回条数，可查询例如“昨天某一时间段的 5 条对话”；Router 结合用户时区解释日期，工具使用明确的时间边界。
- 关键词、时间范围、条数可组合使用，也可只按时间范围或最近条数查询；返回当前数字人私聊中已保存、允许访问的用户消息与 Bot 回复。
- 查询范围覆盖符合条件的已保存历史，不再固定先截取最近 100 条再搜索；先按条件筛选，再按指定顺序和条数返回。
- 支持分页或游标，返回是否仍有结果和下一页位置，便于 Router 少量读取、按需继续，避免一次搬入大量聊天。
- 返回消息标识、角色、时间和必要的任务、成果关联。长消息应明确标记截断并提供继续读取方式，不能因先截断正文而漏掉后部关键词匹配。
- 通过合理的单次条数与内容预算控制开销；具体默认值和上限在实施时确定，不把所有历史一次性注入 Router。

实现：`chat_recent` / `chat_search` 支持 from、to、limit、author、order、cursor，默认 5 条、最多 20 条；查询当前 Bot 当前私聊的完整保存历史，包含附件名搜索。`chat_read` 按消息 ID 和 offset/length 继续读取截断原文，撤回消息与内部 Worker 原文不暴露。

实施边界：时间是毫秒时间戳或显式时区 ISO 字符串，起止均含边界；默认从新到旧、可选升序，游标绑定查询条件与私聊。每轮仍最多 4 次读取、单次不超过 4000 字符、合计 8000 字符，超长记录带截断与续读标记。

## 5. 在聊天输入框旁提供直接停止执行的按钮

状态：已实现，未部署。

- 在聊天输入框所在行，任务执行时显示停止按钮，提供类似终端 Agent interrupt 的明确操作入口。
- 点击后直接调用宿主的停止控制接口，复用现有停止能力，打断当前 Worker，无须等待 Router 理解聊天指令或结束当前推理轮次。
- 按钮在请求中显示“正在停止”，以宿主确认的实际执行状态更新界面，不提前声称已经停止。
- 同步使相关的 Router 未提交派工决定失效，避免停止之后旧决定又启动或恢复执行；防止旧的任务回复在停止后继续交付。

实现：输入框同一行提供直接停止按钮，优先停止正在执行的任务，其次等待确认/恢复、待验收、排队任务。请求中显示“正在停止”，失败可重试并复用请求 ID，版本冲突刷新状态。宿主使未提交的 Router 推理轮次失效，并将当时尚未处理的输入标为可重试，防止旧消息重新派活；停止中收到明确“继续”仍可登记恢复意图。尚未生成工单的 Router 纯推理不在本次按钮控制范围。
