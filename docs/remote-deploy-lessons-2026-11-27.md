# CE 远程同步部署复盘：踩坑与经验（2026-11-27）

对象：ce服务维护@个人服务器（/root/ce_server）上的 CE 服务。
范围：核对版本 → 推送/拉取 → 远程构建 5 个二进制 → 替换运行中的服务并重启。
结果：最终运行的是 260e584 构建，运行进程 / 磁盘 / dist 三者哈希一致；中途多重启了一次，有过约 5 分钟"内存新版、磁盘旧版"的临时不一致。

时间线（均为远程主机本地时间）：

| 时间 | 事件 |
|---|---|
| 15:15 | 远程构建成功（首次因缺 croner 失败，补装后重建） |
| 15:23:12 | 第一次替换 + 重启；新进程 5 秒起来，但兜底脚本误判失败并回滚磁盘文件 |
| 15:23–15:28 | 内存跑新版、磁盘是旧版；远程通道卡住，查不出原因 |
| 15:28:31 | 第二次替换 + 重启（修正探测方式），RESULT=OK |

## 坑 1：把随机端口当成固定端口，写死探测导致误判回滚

**发生了什么**
验收要求"重启后端口 45955 正常监听"。兜底脚本固定轮询 `127.0.0.1:45955/control/state`，60 秒没探到就判定新进程没起来：先尝试直接拉起，仍探不到 → 回滚旧二进制。实际上新进程 5 秒就起来了，只是端口变成了 41489。

**根因**
`src/cli/main.ts` 里 hook/control 服务是 `Bun.serve({ port: 0 })`，端口由系统每次启动随机分配，真实值只写在 `~/.ce/daemon.json` 的 `port` 字段。45955 是上一次启动碰巧分到的，我把它当成了固定配置。

**教训**
- "上次是这个端口"不等于"端口是固定的"。写探测前先看端口怎么来的。
- 一个错误的判据，比没有判据更糟：没有兜底顶多是盲等，错误兜底会把已经成功的部署回滚掉。

**下次做法**
- 探测前先读端口：`PORT=$(grep -o '"port":[0-9]*' ~/.ce/daemon.json | grep -o '[0-9]*')`，每轮探测都重新读（重启过程中 daemon.json 会被重写）。
- 验收/报告里不要把某次观察到的端口写成固定值，写成"daemon.json 记录的端口在监听"。

## 坑 2：回滚只凭单一信号

**发生了什么**
回滚条件只有一个：45955 上 60 秒探不到 `/control/state`。没有交叉验证进程是否存在、`/proc/<pid>/exe` 是什么、48731 单例端口是否被占。于是一个端口错误直接触发了完整的回滚动作。

**根因**
把"某个地址没响应"等同于"服务没起来"。两者不是一回事：可能是端口错了、探测时机太早、或服务起来了但另一个接口没就绪。

**教训**
回滚是破坏性动作，触发条件应当比"没探到"更严格；并且回滚本身也必须校验结果。

**下次做法**
回滚前至少同时满足以下多条再动手：
1. `~/.ce/daemon.json` 不存在，或其中 pid 进程已不存活（`kill -0`）；
2. 单例端口 48731 没有被任何进程监听（`ss -ltnp | grep 48731`）；
3. `pgrep -af '<二进制路径> --daemon'` 无结果；
4. 持续时间超过一个明确的宽限期（新进程 5 秒就起来，给 60 秒足够）。
成功判据同样要多信号：daemon.json 中 `starting:false` + 该 pid 的 `/proc/<pid>/exe` 哈希等于新包哈希 + 该端口 `/control/state` 返回的 pid 与之一致 + `wsConnected:true`。

## 坑 3：假定 systemd 在管服务

**发生了什么**
执行前先查了启动方式，发现 systemd **user** 单元 `~/.config/systemd/user/ce.service` 是 enabled，但状态是 `failed (start-limit-hit)`，自 2026-09-22 起一直如此。真正运行的是手动起的 `/usr/local/bin/ce --daemon`（父进程 1）。

**根因**
install.sh 会装这个 user 单元，容易默认"有单元 = 单元在管"。实际上它两个月前就起不来了，服务一直靠手动起的进程在跑。

**教训**
这次没有踩进去，是因为先查了 `systemctl --user status` 和进程树。如果直接 `systemctl --user restart ce.service`，结果会是重启一个起不来的单元，旧进程照跑，新二进制不生效，还可能多出一个抢单例锁的失败进程。

**下次做法**
- 动服务前先看三样：进程命令行与父进程、对应 unit 的 `ActiveState` / `MainPID`、`daemon.json`。三者对得上才用 systemd。
- unit 是 failed 且 MainPID=0 时，走项目自己的路径：`.new` + `rename` 原子替换 → `127.0.0.1:$PORT/control/restart`。
- 不要顺手去修那个失效单元，那是另一件事，要单独说明并征得同意。

## 坑 4：重启后远程通道卡死，干等了好几分钟

**发生了什么**
被重启的正是承载远程命令通道的 daemon 本身。重启后 `remote_run` / `remote_poll` 持续报"连接中断"或"电脑未授权或已移除"，而被控机其实早已恢复。我等了约 4 分钟毫无进展，还去找了本机有没有 SSH 直连途径（没有）。

**根因**
本地这一侧的远程会话没有随对端重启而重建，处于陈旧状态；错误信息指向"对端"，掩盖了真实原因。

**教训**
"对端没响应"和"本地的会话过期了"表现一样。先排除本地会话问题，再怀疑对端。

**下次做法**
daemon 重启后等 20–30 秒，连接仍失败就 `remote_close` 该 computerId 再 `remote_run`。本次两次都是这样立刻恢复的。

## 坑 5：构建时补装依赖，报告里差点漏掉

**发生了什么**
远程 `sh scripts/build-binaries.sh` 第一次直接失败：`Could not resolve: "croner"`。260e584 这个提交新增了 `croner` 依赖，远程的 node_modules 是旧的。`bun install --frozen-lockfile` 补装 croner@11.0.1 后重建成功。

**根因**
拉代码后没有同步依赖。项目惯例是构建脚本不管 `bun install`。

**教训**
- 补装依赖是对远程主机的实际改动（只写了 /root/ce_server/node_modules，未动全局），必须在结果里如实写出来，不能只说"构建成功"。
- 新包第一次没能构建成功，这一点也要写。

**下次做法**
- 远程拉取后、构建前，先 `bun install --frozen-lockfile`（按 lockfile，不引入范围外的版本）。
- 报告里把"中途做过什么改动"单列：装了什么、写到了哪里。

## 坑 6：对外报告的端口没有核实

**发生了什么**
替换任务的验收里直接写了"端口 45955 正常监听"，这个值来自上一轮核对报告里的观察值。我在执行前没有质疑它，导致兜底脚本的判据从一开始就是错的。直到排查误判原因才查到端口是随机的。

**根因**
把观察值当成了不变量，并且一路把它写进了后续的验收标准和脚本里。

**教训**
从报告里抄来的数字，在用它做判断之前要回到源头确认它是怎么产生的。

**下次做法**
- 核对报告里对端口这类字段的描述要带上来源和性质："本次观察为 45955（启动时随机分配，见 daemon.json）"，避免下游当固定值使用。
- 写自动化前，对每个用到的常量问一句"这个值会不会变"。

## 版本标签不能当版本号（相关但未造成问题）

`VERSION` 是构建时从 package.json 注入的标签，不是 commit。260e584 没改 package.json，所以新旧二进制都显示 `v0.1.0-directory-approval`。本次判断"是否新版"全程用的是 sha256（运行进程 exe / 磁盘 / dist 三者一致），没有依赖标签。另外 Bun `--compile` 会把构建路径嵌入产物，不同机器构建的同一提交哈希不同，跨机比较只能比同一台机器上的 dist 与已安装文件。

## 已落实 vs 尚未落实

**本次已经做到的**
- 替换前备份旧二进制并校验哈希（`/root/ce_server/dist/deploy/backup/ce-linux-x64.03bb47d`，sha256 `78fc4a04…`）。
- 新二进制先暂存为 `.new`、校验哈希后再 `rename` 原子替换。
- 重启走项目自己的 `/control/restart`，没有动 ce-relay / ce-agent 等无关服务，也没有碰失效的 ce.service。
- 第二次重启的脚本改为从 daemon.json 动态读端口，并用多信号判据（pid 存活 + exe 路径与哈希 + `/control/state` 的 pid 一致）。脚本和日志留在远程 `/root/ce_server/dist/deploy/`。
- 最终状态核实了：单实例、三处哈希一致、`wsConnected:true`、Jupyter 复用、配对与授权保留。

**第二次脚本仍然欠缺的（如实）**
- 回滚触发条件还是只有"探不到"这一个信号，没有加上 48731 / 进程存在性的交叉验证。因为第二次重启正常，这个分支没有被执行到，不能说它已经被验证过。
- 重启后 `remote_close` 这一步是人工做的，脚本里不涉及。

**尚未落实、仅作建议**
- `ce.service` user 单元仍处于 failed，开机自启实际不可靠。修复需要改远程主机上的 systemd 配置，本次未做。
- ce 的本机端口随机分配这一点，让任何外部探测都必须先读 daemon.json。如果希望外部运维更简单，可以考虑让 ce 把端口写到一个稳定位置或支持固定端口——这是代码改动，本次未做，是否要做由 owner 决定。
- `scripts/build-binaries.sh` 不会自己跑 `bun install`，可以在脚本里加一步或在前置检查里提示依赖缺失——同样是代码改动，未做。
- 兜底逻辑目前是临时脚本。如果要长期用，应当并进项目的更新流程并补测试，而不是留在 dist/ 里（dist 是 gitignored 的，不会进仓库）。

## 一页检查单（下次远程替换 CE 服务时）

1. 查进程树与 unit 状态，确认到底是谁在管服务。
2. 读 `~/.ce/daemon.json` 拿当前 pid / 端口，不用历史值。
3. 备份旧二进制，校验哈希。
4. 新二进制 `.new` 暂存 → 校验哈希 → `rename` 替换。
5. `curl 127.0.0.1:$PORT/control/restart`，脚本用 `setsid nohup` 脱离终端。
6. 等 20–30 秒；通道不通就 `remote_close` 后重连。
7. 核实：单实例、`/proc/<pid>/exe` 哈希 = 磁盘 = dist、`starting:false`、`wsConnected:true`。
8. 回滚只在多信号同时指向"没有 daemon 在跑"时才执行，回滚后同样核实。
